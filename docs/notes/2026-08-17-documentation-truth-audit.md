# Documentation Truth Audit

**Date:** 2026-08-17
**Method:** Probe, don't read. Every load-bearing claim is checked against the
code, with the command recorded so a reviewer can re-run it.
**Scope:** Every document that survives the documentation-architecture change,
plus every document being harvested. Package-level doc comments included;
inline comments excluded.

## Verdict key

| Verdict | Meaning | Action |
|---|---|---|
| TRUE | Claim holds | Leave |
| DOC WRONG | Document contradicts the code | Fix the document |
| DOC RIGHT, CODE WRONG | The document states the intended bar; the code does not meet it | Fix the code. **Never weaken the document.** Becomes a successor work item |
| UNVERIFIABLE | Nothing can confirm the claim | Delete the claim |
| HOMELESS RULE | The claim's only source is a document being deleted | Needs an ADR or promotion before that document goes |

**UNVERIFIABLE has two subspecies, and they take different actions.** Only
write bare `UNVERIFIABLE` for a claim that is inherently unconfirmable —
nothing in any environment could probe it (e.g. it depends on a private,
undocumented intent, or a value that genuinely leaves no trace anywhere).
For that kind, "delete the claim" is correct.

A claim that *could* be probed but wasn't — because the tool, network, or
credential needed wasn't available at audit time — is a different thing
and must be recorded as **UNVERIFIABLE (blocked)**, with the exact
failing command and error pasted in evidence. "Delete the claim" does
**not** apply to `UNVERIFIABLE (blocked)`: deleting on a blocked probe
risks deleting a true statement for no reason but bad luck with
connectivity. A `UNVERIFIABLE (blocked)` row must be re-probed with a
working path before any action is taken on it — do not let "blocked"
silently decay into "false" by inheriting the inherent-UNVERIFIABLE
action. (This distinction exists because a prior pass in this audit
recorded two GitHub-API-dependent claims as bare UNVERIFIABLE after `gh
api` returned HTTP 503 in a network-blocked sandbox; a later re-probe with
working network access found both claims TRUE. Had "delete the claim"
been applied on the strength of the blocked verdict, it would have
deleted two accurate statements. See the CONTRIBUTING.md/AGENTS.md and
CODE_OF_CONDUCT.md sections below for the corrected rows and the
re-probe evidence.)

Probed each part separately, across all 8 registered differs
(`synth.NewSignalDiffer`, `NewFaultDiffer`, `NewDetectorDiffer`,
`NewDMSDiffer`, `NewTrafficIntervalDiffer`, `NewZoneIncidentDiffer`,
`NewZoneIntervalDiffer`, `NewCCTVDiffer` — the same 8 confirmed registered
in `internal/app/app.go` above), not just "some test exists somewhere."

```

(full output: 45 tests across `signal_test.go`, `fault_test.go`,
`detector_test.go`, `dms_test.go`, `trafficsensor_test.go`,
`perception_test.go`, `cctv_test.go` — see git history for the complete
list; representative names quoted below)

**Part 1 — first poll.** Every one of the 8 differs has a dedicated
first-poll test: `TestFirstPollEmitsOnlyStatusReport` (signal),
`TestFirstPollRaisesEverythingCurrentlyRaised` (fault),
`TestFirstPollEmitsNoReport` (detector), `TestDMSFirstPollEmitsNothing`
(dms), `TestTrafficDiffer_FirstObservationEmits` (traffic-interval),
`TestZoneIncidentDiffer_FirstObservationDetectsStandingIncidents` /
`TestZoneIntervalDiffer_FirstObservationEmits` (perception, both
differs), `TestCCTVDiffer_FirstObservationEmitsNothing` (cctv). **8/8. Holds.**

**Part 2 — no change.** Direct, dedicated tests exist for 7/8:
`TestUnchangedFaultSetEmitsNothing`, `TestDMSNoChangeEmitsNothing`,
`TestTrafficDiffer_SameIntervalReReadEmitsNothing`,
`TestZoneIncidentDiffer_NoChangeEmitsNothing`,
`TestZoneIntervalDiffer_SameIntervalReReadEmitsNothing`,

```

```
$ cat internal/synth/signal_test.go
```
(4 tests total: `TestFirstPollEmitsOnlyStatusReport`,
`TestTransitionsEmitChangeEvents`, `TestFailedFacetSuspendsDiffing`,
`TestEngineCopiesDeviceKindOntoEvents`.) The one test that touches

**Part 4 — failed read.** This is a shared Engine mechanism, not
per-differ logic:

```
$ cat internal/synth/synth.go
```
`Engine.Apply` (`internal/synth/synth.go`) only calls a differ for facet
kinds present in `snap.Facets`; a facet that failed to read is recorded
in `snap.Errors` instead and is simply never in `snap.Facets`, so its
differ is never invoked and `dev[kind]` (remembered previous state) is
left untouched — identical code path for all 8 differs. This is proven
directly for 4 of them (`TestFailedFaultReadNeverClears`,
`TestFailedDetectorReadEmitsNothing`, `TestDMSFailedReadEmitsNothing`,
`TestFailedFacetSuspendsDiffing` for signal) and, because the mechanism
lives in the shared `Apply` loop rather than in any individual `Diff`
implementation, that is sufficient to cover the other 4
(trafficsensor/zone-incident/zone-interval/cctv have no differ-specific
failure path to test separately). **Holds.**
